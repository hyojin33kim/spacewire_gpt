# Encoding §5.4 Semantic Consistency Review

Status: **Draft — Golden Model coding gate not yet open**

## Result

The §5.4 normative slice is now represented by **56 atomic requirement entries** and mapped to five behavior contracts. The remaining risk is not missing §5.4 prose; it is **cross-clause semantics and source inconsistencies**.

## Findings

| ID | Finding | Class | Disposition |
|---|---|---|---|
| CR-ENC-001 | §5.4.3.4 parity depends on the previous encoded character payload plus the current parity/data-control flag. It is not a stateless per-character parity function. | Golden Model state | Keep previous-character parity context explicitly. |
| CR-ENC-002 | §5.4.8.c permits a disconnect detection threshold within the stated timing bounds; it does not define one FPGA counter value. | RTL contract boundary | Golden Model models the timing rule/range; clock/counter mapping waits for RTL contract. |
| CR-ENC-003 | §5.4.4.e controlled reset has a 500 ns minimum and an implementation-dependent upper bound. | RTL contract boundary | Do not hard-code one cycle count in protocol model. |
| CR-ENC-004 | §5.4.10.3 maximum signalling rate depends on attenuation, skew, jitter and correct decoding. | System/physical boundary | Treat as implementation capability/configuration, not protocol constant. |
| CR-ENC-005 | §5.4.2 behavior is exposed through §6.3 service primitives. A Golden Model that only models characters without enable/status semantics would be incomplete. | Cross-clause dependency | Added BC-ENC-PIPE-001 and BC-ENC-IF-001. |
| CR-ENC-006 | §6.4 defines DS_TX.request and DS_RX.request between Encoding and Physical layers. This dependency was not explicit in the first baseline. | Cross-clause dependency | Add §6.4 to Encoding interface slice before Golden Model API freeze. |
| CR-ENC-007 | §6.3.2.5 defines RECEIVE_ERROR.indication(RX_Error_Flags), with parity or ESC error type. The §5.4.2 status flag alone does not capture this parameterization. | Interface detail | Golden Model event must carry error kind or equivalent typed event. |
| CR-ENC-008 | §6.3.2.6.4 says gotNull.indication effect is according to the state machine of **clause 5.5.6**, while the link initialisation state machine is specified in §5.5.7 / Figure 5-19. | Source cross-reference inconsistency | Do **not** silently correct. Record as spec issue; use §5.5.7 only after explicit interpretation decision. |
| CR-ENC-009 | Definitions (§3.2.41/§3.2.46), §5.4.6 and §6.3.2.6 jointly constrain "first Null": receiver enabled, no parity error, gotNull lifetime until RX Enable deassertion. | Semantic merge | Maintain as one canonical FIRST_NULL/GOT_NULL concept with multiple evidence links. |

## Golden Model gate

Before Python implementation starts:

1. Atomic-extract the relevant §6.3 and §6.4 service primitives, or approve an explicit abstraction boundary.
2. Resolve CR-ENC-008 as an interpretation record, without modifying the source wording.
3. Define typed receiver events: `parity_error`, `ESC_error`, `disconnect`, `gotNull`.
4. Freeze the §5.4 behavior-contract schema as Encoding semantic baseline v0.1.

Only after those four items should the executable Encoding Golden Model become the next source artifact.
